# 02 设计原则：为什么这个仓库长这样

> 本文来源：[.agents/invocation.md](../.agents/invocation.md)、[CLAUDE.md](../CLAUDE.md)、[SCOPE.md](../SCOPE.md)、[.out-of-scope/new-skills.md](../.out-of-scope/new-skills.md)

这一章讲贯穿全部 38 个 skill 的系统级设计决策。读完它，后面每个 skill 的"为什么"都有了坐标系。

## 原则一：调用权限二分——user-invoked vs model-invoked

仓库的唯一分类轴不是"功能"，而是**谁能调用它**（见 [invocation.md](../.agents/invocation.md)）：

| | user-invoked（用户调用） | model-invoked（模型调用） |
|---|---|---|
| 谁能触发 | **只有人类**手动输入命令（如 `/grill-me`） | 模型自动调用，人类也可以手动 |
| 技术标记 | `disable-model-invocation: true`（Claude Code）+ `policy.allow_implicit_invocation: false`（Codex） | 两者都不设置（默认） |
| description 写给谁看 | **人类**：一行摘要，给浏览斜杠命令列表的人看 | **模型**：保留丰富的触发短语（"Use when the user wants…"） |
| 角色定位 | **编排者**（orchestrator）：负责流程编排 | **纪律承载者**：可复用的方法论 |

**为什么这样设计？**

1. **防止 skill 乱触发**。一个 user-invoked skill 被两个开关（Claude 和 Codex 各一个）双重排除在模型的可达范围之外。没有任何其他 skill 能调用它——这是硬保证，不是提示词层面的"请不要"。
2. **判断标准很清晰**：一个 skill 该不该保持 model-invoked，就看一条——*模型能不能有用地自主使用它？*（注意：能被复用只是抽取出 skill 的**理由**，不是让它 model-invoked 的**标准**。）
3. **调用方向形成单行道**：user-invoked 可以调用 model-invoked，反之绝不行，user-invoked 之间也不能互调。这保证了流程的"入口"永远由人类掌控，而"怎么做好一件事"的纪律可以被任何入口复用。

**例子**：`/grill-me`（user-invoked）是入口，它内部调用 `/grilling`（model-invoked）这个"访谈原语"；`/grill-with-docs`、`/triage`、`/wayfinder`、`/improve-codebase-architecture` 内部也调用同一个 `/grilling`。一份纪律，五个入口。

## 原则二：组合优于配置——Skill tool 显式调用

skill 之间的依赖不用跨目录的文件链接（`../other-skill/FILE.md`），也不留 `/skill` 形式的提及让模型自己猜，而是写成**明确的指令**：

> Call the Skill tool with "grilling"（调用 Skill 工具，参数为 "grilling"）

为什么（invocation.md 给出的理由）：

1. **点名列出工具名才会真的触发**。多数 harness 把 skill 调用暴露为模型可调的工具，把话挑明比在散文里丢一个 `/name` 然后祈祷模型读懂是命令，命中率更高。
2. **不带 `/` 前缀是刻意的 harness 中立**：skill 名字本身不预设属于哪家 harness 的触发语法。
3. **一次调用只带一个 skill**。需要两个就说"Call the Skill tool twice, for X and Y"，而不是含糊的"用它调 X 和 Y"。
4. **共享内容放在拥有它的 skill 里**。别的 skill 要用就调用它，而不是跨文件夹链接。避免了文档漂移。

这条原则的逆命题也一样重要：因为 user-invoked skill 谁也调不了，所以当一个步骤的前置是 user-invoked skill（如 `setup-matt-pocock-skills`）时，指令必须写成对人类说的话："告诉用户去运行 `/setup-matt-pocock-skills`"。

## 原则三：小目录、强策展

这个仓库**明确拒绝新 skill 提案和贡献**（[.out-of-scope/new-skills.md](../.out-of-scope/new-skills.md)）。理由值得细读：

> "目录是我每天自己用的 skill 集合，它是刻意小的。每个 skill 都是永久的维护面：它必须和其他 skill、docs 页、ask-matt 的路由图、插件清单保持同步。skill 越短越少，保持正确的成本就越低。"

作者给自己定的规矩同样适用于外人：**如果能用现有 skill 组合出某个行为，它就不配成为一个新 skill**。多数提案本质上是 `grilling + to-spec + to-tickets + implement` 的某个特定排列，那属于你自己的 prompt 或你自己的 fork。

配套机制还有 [SCOPE.md](../SCOPE.md) 的"准入门槛"：一个 issue 要存活，必须同时满足（1）描述真实会话中观察到的失败（ hypothetical 的"要是能…就好了"不算）；（2）符合哲学（不是配置项、不是某个人的工作流定制）。已拒绝的概念逐条记录在 `.out-of-scope/`，每条都写明理由——**决策也是文档**。

## 原则四：仓库自我管理（吃自己的狗粮）

这个仓库本身就是这些 skill 的第一个用户：

- 仓库有自己的 [`GLOSSARY.md`](../GLOSSARY.md)（Issue tracker、Decision ticket、Triage role 等术语）——这正是 `/grill-with-docs` / `/domain-modeling` 推崇的实践
- `ask-matt` 是路由器，CLAUDE.md 规定：**任何时候增删改一个 user-invoked skill，必须同步更新 ask-matt 的地图**。"一个它从没提到的新 skill，或一个它还在路由的已死 skill，就是一个说谎的路由器。"
- 文档页（`docs/`）与 skill 行为强制同步，模板和规则写在 [.agents/writing-docs.md](../.agents/writing-docs.md)
- 甚至有排版禁令：全文**不许用 em-dash（—）**，句子到了想用破折号的地方就改成逗号、冒号、括号或连词——且明说"永远不要做盲目的字符替换"

## 原则五：上下文是稀缺资源（context hygiene）

`ask-matt` 引入了 **smart zone**（聪明区）概念（[AI Hero 词典](https://www.aihero.dev/ai-coding-dictionary/smart-zone)）：约 150k token 的窗口，模型在其中还能敏锐推理。整个工作流围绕它设计：

- 主线第 1–3 步（拷问 → spec → 工单）保持在**一个不间断的上下文窗口**里，因为 spec 和工单要建立在拷问产生的同一份思考上
- 每张工单是自包含的，所以 `/implement` 逐工单跑、中间 `/clear`，上下文用完即弃
- 接近 smart zone 上限时不要硬撑（"don't push on degraded"，别在降智状态硬推），在最近的**阶段边界**（phase boundary）做处置

**阶段边界决策树**（[PHASE-BOUNDARIES.md](../skills/engineering/ask-matt/PHASE-BOUNDARIES.md)）把"两个阶段之间怎么办"变成五选一的有序提问：

1. 能继续吗（Continue）？→ 成本为零，先排除它
2. 上下文对后面无关吗？→ `/clear`（最便宜的棋，且旧会话仍可恢复）
3. 需要**移交**吗（换 harness / 换目录 / 给同事 / 中途分叉支线任务）？→ `/handoff`
4. 任务能无人值守（AFK）跑吗？→ 派 **subagent**
5. 都不是 → `/compact`（默认的兜底，**而不是第一反应**）

背后的核心权衡是**一手源 vs 二手源**：除 Continue 外的每一步都把"实际发生的会话"（一手源）变成"会话的摘要"（二手源）——信息变少、噪音变少、空间变大。只有当留下的损失大于换来的空间时才值得付这笔账。

## 原则六：人是流程的所有者

贯穿整个仓库的姿态：agent 负责**事实与体力活**，人类负责**决策**。grilling 的设计里明确写着 "facts are the agent's job and decisions are yours"（查证是 agent 的事，拍板是你的事）。user-invoked 只能人来触发、wizard 专门处理"只有人能做的步骤"、to-questionnaire 把问题寄给"唯一能回答的人"——这些都是同一哲学的不同面。
