深模块词汇：codebase-design 的八个词

前置：0003 grilling 实操演练 ｜ 配套阅读：04 · codebase-design 节 · 速查表 ｜ 下一课：待定（告诉我想深入哪块）

本课的目标（一个 Win） 学会这套词汇后，你能指着代码库里的任何一个模块说出：它 deep 还是 shallow？为什么？ ——并且用 deletion test 论证你的判断。这是 /improve-codebase-architecture 找候选、/tdd 选 seam 时共同使用的语言。

1. 为什么需要一套词汇？

SKILL.md 的第一性主张："consistency of language is the whole point"（语言的一致性就是全部重点）。 设计对话里 "component / service / API / boundary" 各说各话——没人一致使用的术语比没有术语更糟。 这套词汇源自 Ousterhout《A Philosophy of Software Design》和 Michael Feathers 的 seam 概念， 但被作者改造过（见第 4 节）。

2. 八个词

术语定义避免说
Module有 interface 和 implementation 的任何东西（刻意的 scale-agnostic：函数/类/package/跨 tier 切片）unit, component, service
Interfacecaller 正确使用该模块必须知道的一切：类型签名之外，还有 invariants、顺序约束、error modes、性能特征API, signature（太窄）
Implementation模块内部代码体（讨论"大/小"时用）
Depthinterface 处的 leverage：caller 每学一单位 interface 能驱动多少行为行数比
Seam不改此处代码就能改变行为的地方（Feathers）；是 interface 的位置——seam 放哪本身是独立设计决定boundary（与 DDD 撞词）
Adapter在 seam 处满足 interface 的具体物；描述角色（填哪个槽）而非实质
Leveragecaller 从 depth 得到的：每单位所学 interface 的能力
Localitymaintainer 从 depth 得到的：变更/bug/验证集中一处，"fix once, fixed everywhere"

一个记忆钩子：depth 的两个受益者是 caller（leverage）和 maintainer（locality）。 adapter 的两种典型比例：Postgres repo 是"小 adapter + 大 implementation"；in-memory fake 是"大 adapter + 小 implementation"。

3. 四条原则

  1. Depth 是 interface 的属性，不是 implementation 的——deep module 内部可以由小的可替换部分组成，只是不进 interface；模块可有 internal seams（私有、自己的测试用）和 external seam。
  2. The deletion test：想象删掉模块——复杂度消失 = 它只是 pass-through；复杂度在 N 个 caller 身上重现 = 它在挣饭吃。下面马上练。
  3. Interface 即 test surface：caller 和测试过同一个 seam；想测到 interface 之外 = 模块形状不对（这正是 /tdd "只在约定的 seam 测试"的理论根基）。
  4. One adapter means a hypothetical seam. Two adapters means a real one.——没有东西真的跨 seam 变化，就不要切 seam；单 adapter 的 seam 只是 indirection。

4. 一个精妙的改造：depth ≠ 行数比

Ousterhout 原版用"implementation 行数 / interface 行数"定义 depth。 这个仓库拒绝了它——那会奖励往 implementation 里灌水。 替代定义：depth-as-leverage，caller 每学一单位 interface 能驱动多少行为。

这也是 leading word 的活例子（writing-for-agents 的概念）：这些词是"预训练里已有的紧凑概念"， /tdd、/improve-codebase-architecture、/to-spec 的 Implementation Decisions 都用同一套 token 说话，agent 一看到 "seam" 就招募起一整片行为。

5. Deletion test 三连练

看代码 → 判断 → 点击即反馈。（先自己判断再看答案！）

练习 A：

// services/user-service.ts
export function getUser(id: string) {
  return prisma.user.findUnique({ where: { id } });
}

删掉它，每个 caller 直接调 prisma.user.findUnique。这是 deep 还是 shallow？

✅ 删掉后什么都没丢：一行转发、一个参数、一个返回——interface 和 implementation 一样复杂。它是 pass-through。注意：不是说它"有罪"，而是它不构成一个深模块；它甚至不该存在（caller 直接调 prisma 即可），或者只是等待长出行为的地方。

练习 B：

// pdf-invoice.ts
export interface InvoiceRenderer {
  render(invoice: Invoice): Promise<Blob>;  // 唯一入口
}
// implementation（约 800 行）：排版、多币种、
// 税务规则、中文字体嵌入、自动分页……

删掉它，复杂度去哪？

✅ 删掉后 800 行复杂度在 N 个 caller 身上重现（或根本没人能重现）。一个方法的小 interface 驱动大量行为：leverage 极高，locality 也高（改税务规则只动一处）。教科书级 deep module。

练习 C：

// editor.ts —— 40 个 public 方法，共约 120 行实现
export class Editor {
  insertText(t: string) { ... }
  deleteSelection() { ... }
  moveCursor(dx: number, dy: number) { ... }
  getCursor() { ... }  // ……还有 36 个
}

行数不少，但它是 deep 还是 shallow？

✅ 这就是"depth 是 interface 的属性"的考场：40 个 public 方法 ≈ 120 行实现——caller 必须学 40 个单位才能驱动这点行为，leverage 极低。深化的方向不是"加实现"，而是把 40 个方法收进少数高层入口（如 apply(edit: Edit) + 事件流）。

7. 检验一下

1. depth 在这套体系里被定义为什么？

✅ depth = interface 处的 leverage：caller 每学一单位 interface 能驱动多少行为。行数比定义被明确拒绝（奖励灌水）。

2. deletion test 的判据是什么？

✅ 复杂度消失 = pass-through；在 N 个 caller 身上重现 = 它在挣饭吃（deep 的信号）。

3. "One adapter means a hypothetical seam" 警告什么？

✅ 没有东西真的跨 seam 变化就不要切 seam——单 adapter 的 seam 只是 indirection。两个 adapter（如 Postgres repo + in-memory fake）才证明 seam 是真的。

4. 为什么拒绝"实现行数 ÷ 接口行数"的 depth 定义？

✅ 行数比可以靠膨胀 implementation"刷高"，但不增加 caller 得到的 leverage。depth-as-leverage 直接度量受益者（caller 和 maintainer）得到的东西。

8. 收尾
