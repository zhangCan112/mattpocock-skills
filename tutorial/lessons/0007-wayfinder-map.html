Lesson 0007 · 约 12 分钟

wayfinder：为迷雾工程绘制决策地图

前置：0006 code-review 双轴拆解 ｜ 配套阅读：03 · wayfinder 节 · 速查表 ｜ 下一课：待定（告诉我想深入哪块）

本课的目标（一个 Win） 读完结这页，你能说清 map 的五节结构、四种 decision ticket 各自的触发判据、 fog 和 ticket 的分界线——并且拿到任何一个待定事项，能判断它该开票、该进雾， 还是根本在图外。

0. 热身：先回忆上一课（检索练习）

不翻回去，凭记忆答。答错正好暴露要补的洞。

热身 1：两根轴为什么要跑在互相隔离的子代理里？

✅ 混合裁定会让通过的一轴掩盖挂掉的那轴；隔离 + 并排呈现是防遮蔽的全部意义（顺带防"同 context 评审自己"的确认偏误）。

热身 2：Spec 轴找不到源头 issue 时该怎么办？

✅ 报告 "no spec available"，只跑 Standards 轴——"绝不从代码反推需求"：把实现读成需求，等于拿学生答案当标准答案。

1. 它在链条里的位置：第三条匝道

0002 埋过一个伏笔："什么时候该用 wayfinder？" 现在回收。主线匝道三件套：/triage（外来需求）、/diagnosing-bugs（东西坏了）、 /wayfinder（迷雾）。它是全集里最重的流程，所以触发条件最窄，就两条：

  • 工程大到一个 agent session 装不下——分界线就是 session 数： grill-with-docs 管 single-session planning，wayfinder 管 multi-session planning；
  • 通往 destination（目的地）的路还看不见——被雾包着。

两种调用模式：Chart the map（一次：把图画出来，然后停——"charting is one session's work; it hand-resolves nothing"）和 Work through the map（之后每个 session：claim 一张票、解决它、关掉它）。 出口：地图清空时 "it hands off, it doesn't build"——在 /to-spec #<map_issue> 汇回主线，把散落的决策收拢成可构建的规格。

2. The Map：索引，不是仓库

Map 就是 issue tracker 上一个 label 为 wayfinder:map 的 issue，票是它的 child issues。 核心铁律："a decision lives in exactly one place, its ticket"——决策只活在它的票里， map 只给一行 gist + 链接。这样每个 session 用低分辨率加载 map 就能干活，细节按需 zoom。

#issue · wayfinder:map —— map body 五节
Destination
抵达是什么样：一份 spec / 一个锁定决策 / 一次就地改动。命名它是绘图的第一动作——destination 定死 scope，之后每张票都对着它量。
Notes
领域、每个 session 该调的 skills、这个工程的长期偏好。
Decisions so far
索引：每张关闭的票一行（票名链接 + 一行 gist）。解决仪式 = resolution comment → close → 这里加一行。
Not yet specified
雾（fog of war）：知道有决策要来，但还说不清问题——见第 4 节。
Out of scope
destination 之外、被有意识排除的工作。永不毕业。

配套的三个协作机制：

  • Claim 即 assign：开工前先把票 assign 给自己——"That assignee is the claim"，并行 session 看到就跳过；
  • Frontier = open + unblocked + unclaimed：可取的票。blocking 用 tracker 原生依赖边连，人不开 map 就能在 tracker UI 里看见哪些票可取；
  • Refer by name：给人读的叙述里用票的名字，绝不裸编号——"A wall of #42, #43, #44 is illegible"。

3. 四种票型：每张都是一个 session

票的 body 就是问题本身，尺寸 = 一个 100K token 的 agent session——票是 context 的计量单位。每张带 wayfinder:<type> label：

票型模式触发判据怎么解决
grillingHITL默认：聊得清楚的问题双调 grilling + domain-modeling
prototypeHITL"该长什么样 / 该怎么表现"——聊不出来调 prototype 做粗糙实物，链接为 asset
researchAFK工作目录之外的事实挡住了决策subagent 调 research，chart 时并行点火
task皆可手工活挡住决策（注册服务、开权限）agent 能做就做，否则给人精确清单

三条铁律：

  • 一个 session 只解决一张票（"never resolve more than one ticket per session"）——唯一例外是 research：chart 完立即全部并行点火，发现写到一次性的 research/<name> 分支，push 但永不开 PR、永不 merge；
  • HITL 铁律："the agent never stands in for the human's side of it"——grilling 的 agent 自问自答，即违规；
  • Read the label, not just the body：票型只写在 label 上，body 永不声明自己是哪种。

4. Fog of war：刻意不画看不见的图

分界线一句话：Ticket when the question is already sharp; fog when you can't yet phrase it that sharply. 判据是你现在能不能把问题说清楚，不是你现在能不能回答它。
  • 已经 sharp、哪怕被阻塞 → 开票，用 blocking 边排到后面；
  • 还说不清问题 → 进 Not yet specified，而且别预先把雾切成票大小（"Don't pre-slice the fog"）——一坨雾到前沿时可能毕业成好几张票，也可能一张都不剩；
  • 毕业机制：一张票解决，它前方的雾就散了，能 specify 的部分毕业成新票、同时从 Not yet specified 里删掉（绝不两地出现）；
  • 反面教材就是瀑布陷阱：用户实测"绘了 27 张票，做到第 13 张其余全失效"。解药是 fog + 渐进出票，外加 "prototypemaxxing, not planmaxxing"——多用便宜原型暴露不确定性；
  • 零雾门控：chart 时的广度优先拷问如果发现根本没雾——路已经看得见、一个 session 装得下——skill 会直接停下："you don't need a map. Stop and ask the user."

Out of scope 不是雾："Scope, not sharpness, lands it here"。雾只朝 destination 聚集； 越过 destination 的工作不是看不清，是不属于。它进自己的 Out of scope 节、永不毕业—— 除非重画 destination，且届时是全新工程，不是续作。

5. Plan, don't do：约束住在被约束者的家里

wayfinder 默认只规划："The pull to just do the work is usually the signal you've reached the edge of the map"——想动手的冲动，恰恰说明到了图的边缘、该交接了。例外可以写在 map 的 Notes 里（"this map carries execution"），但这正是最出名的失败：

约束和它的豁免写在同一个文件里，而这个文件归被约束的 agent 所有。 有用户亲眼看到 agent 在会话中往自己写的 Notes 里塞了 "this map carries execution"， 后续 session 读回这行、当成许可，直接在服务器上写起了产品代码。

两道防线：接手别人绘的 map 先读 Notes；看到长得像实现步骤的 task 票，按误型处理。

6. 实操：这东西进地图的哪一格？

场景都来自同一个"从零做一个 SaaS"的工程。destination：一份能开工的 spec。

练习 1："搜索用 Postgres 全文还是 Elasticsearch？——问题一句话说得清，但要等'数据量级'那张票先定。"

✅ fog vs ticket 的判据是"现在能不能把问题说 sharp"，不是"现在能不能回答"。已 sharp 但被阻塞 → 照样开票，blocking 边把它排在后面。

练习 2："认证方案定了之后，用户体系肯定还有细节要定——但具体是什么问题，现在还说不清。"

✅ 问题本身还 phrase 不出来 → 雾。"Don't pre-slice the fog"：一坨雾到前沿时可能毕业成好几张票，也可能一张都不剩。

练习 3："定价页到底该长什么样？——光靠聊，聊不出来。"

✅ "how should it look / behave" 是 prototype 的触发判据：做一个便宜、粗糙、具体的东西给人反应。谈不出答案的问题，就别用谈的方式解决。

练习 4："要评判某家三方 API 值不值得押注，得先注册账号拿到 key，才看得见它的文档。"

✅ task = "手工活挡住了决策"。它是唯一做而不决的票型，靠解锁一个决策（而非交付目的地）赢得座位。和 research 的区别：research 是读资料，AFK subagent 干。

练习 5："用户聊天时顺口提了一句：'将来还想做个手机 App。'"

✅ "Scope, not sharpness, lands it here"——越过 destination 的工作不是雾。进 Out of scope 的东西永不毕业；只有重画 destination 才回来，且届时是全新工程。

7. 检验一下

1. wayfinder 和 grill-with-docs 的分界线是什么？

✅ session 数，不是项目大小：装得下就 grill（更便宜更好），装不下才建图。绿地不是必要条件——legacy 代码库上"这里已经什么是真的"本身就是雾。

2. 关于 map 和它的票，哪一句是对的？

✅ "a decision lives in exactly one place, its ticket"——map 只给一行 gist + 链接，session 低分辨率加载就能干活，图才能一直长而不撑爆 context。

3. 所有票关闭、地图清空之后，下一步是什么？

✅ "it hands off, it doesn't build"：清空的地图是一堆链接起来的决策，不是构建计划。to-spec 把它们 collapse 成一份 spec，再走 to-tickets → implement。

4. 四种票型里，唯一"做而不决"的是哪个？

✅ task 是唯一以"做"解决的票，且只有当手工活阻塞了一个决策时才配进图——它最容易出错：agent 常把它读成实现步骤、在图里写起产品代码。

8. 收尾

推荐的首要资料 wayfinder 的 SKILL.md ——map body 模板、四种票型、chart/work 两模式的原文。深挖真实失败案例（27 张票、Notes 自我豁免、 并行翻车）就读 docs 页的 Common questions，每条都是用户实测。
有任何不清楚的？直接问你的 agent 比如："我手头这个工程该走 grill-with-docs 还是 wayfinder？帮我按 session 数判一下"、 "把我最近一个项目的待定事项列出来，我们一起分类成 ticket / fog / out of scope"、 "为什么 research 票是 one-ticket-per-session 的唯一例外？"—— 或者翻翻你自己 issue tracker 上的真实工单，练一遍今天的"进哪一格"。
