tdd 三大反模式：亲手挑出坏测试

前置：0004 深模块词汇（用到 seam 概念） ｜ 配套阅读：04 · tdd 节 · 速查表 ｜ 下一课：待定（告诉我想深入哪块）

本课的目标（一个 Win） 读完这页，任何一段测试代码放到你面前，你都能说出它是三大反模式里的哪一种（或者根本不是反模式）， 以及怎么改。这是 tdd skill 里最值钱的部分：让测试套件一文不值的失败模式，全在这三个名字底下。

1. tdd 在这个仓库里的角色

/tdd 是 reference（参考规范），不是 driver：它由 /implement（逐票）和 /implement-spec（每个 implementer subagent 内部）驱动。它定义三件事： 什么是好测试、测试住在哪（seams）、循环怎么转。

循环规则含义
Red before green先写失败测试，再写恰好够让它通过的代码；不为未来 anticipation
One slice at a time一个 cycle = 一个 seam + 一个测试 + 一个最小实现；每个测试是 tracer bullet（响应上一轮所学的端到端实弹）
Refactoring 不在循环内2026 年 6 月被移除——agents 几乎从不做那一步；重构归 /code-review（带 Fowler smell baseline）。（趣闻：description 里的 "red-green-refactor" 触发词保留了，是个已知的不一致）

2. 三大反模式

① Implementation-coupled（实现耦合）

mock 内部 collaborator · 测私有方法 · 旁路验证（查 DB 而非用接口）
征兆：重构时行为没变，测试却红了。好测试的判据是"代码可以整个换掉，测试不该跟着变"。

② Tautological（同义反复）

断言的期望值用代码自己的方式重算——构造上必然通过，永远无法与代码不一致。
修法：期望值来自独立 truth（known-good 字面量、worked example、spec）。

③ Horizontal slicing（水平切片）

先写全部测试再写全部实现——批量测试验证的是想象中的行为，在理解实现之前就锁死了测试结构。
修法：一次一个 slice，让每个测试响应上一轮所学（和 /to-tickets 反对横切是同一个道理）。

总纲 + 三问自检 好测试是对行为的独立见证，一片一片地承诺。三个反模式分别打碎其中一个词： 看错位置（实现耦合）、标准不独立（同义反复）、节奏不对（水平切片）。 拿到任何测试，问三句： ① 实现整个换掉（行为不变），它还绿吗？ 不绿 → 实现耦合。 ② 期望值从哪来？ 复跑实现的逻辑或产物 → 同义反复。 ③ 这批测试是理解实现之前一次写完的吗？ 是 → 水平切片。

3. 挑错五连练

每段代码：它是哪个反模式？还是根本没问题？先自己判断，再点击。

练习 1：

test('add sums numbers', () => {
  expect(add(2, 3)).toBe(2 + 3);
});

✅ 期望值 2 + 3 是现场推导出来的，不是引用一个独立标准答案——同义反复的最轻形态。JS 引擎会把它算成 5，所以这一个测试侥幸能抓到手误；但这个形式一旦养成，很快滑向真正的恒真式（toBe(a + b)、期望侧复跑实现的逻辑）。修法：expect(add(2, 3)).toBe(5)——5 是独立字面量，写着"我就知道答案是 5"的承诺。

练习 2：

test('createUser saves to database', async () => {
  await createUser({ name: 'Ann' });
  const rows = await db.query('SELECT * FROM users');
  expect(rows.length).toBe(1);   // 直接查库验证
});

✅ 旁路验证：绕过 public interface 伸进存储层。哪天你把存储换成别的（行为完全不变），这个测试就红了——征兆完全吻合。对照 tests.md 里的 GOOD 版本：createUser makes user retrievable，用 getUserByName('Ann') 经同一个接口取回来验证。

练习 3：

test('checkout validates the cart', () => {
  const spy = jest.spyOn(internals, 'validateCart'); // internals 是模块私有
  checkout(cart);
  expect(spy).toHaveBeenCalled();
});

✅ 两罪并罚：mock 内部 collaborator + 验证"内部调用过什么"而非"外部发生了什么行为"。mocking 规则：只在系统边界 mock（外部 API、时间、随机性）；绝不 mock 自己的模块。行为版写法：给一个空地址的 cart，断言 checkout 返回/抛出可观察的校验错误。

练习 4：

// sprint 计划：
// 第 1 周：写完全部 24 个测试
//   （schema 层 8 个、API 层 8 个、UI 层 8 个）
// 第 2 周：开始实现，逐个让测试变绿

✅ 双重横切：先全部测试后全部实现（批量测试验证想象中的行为），且按技术层分组（和 /to-tickets 反对横切工单同理）。修法：一次一个垂直 slice——schema + API + UI + 测试一起做穿一条用户可面对的行为。

练习 5：

test('createUser makes user retrievable', async () => {
  await createUser({ name: 'Ann' });
  const user = await getUserByName('Ann'); // 同一个 public interface
  expect(user.name).toBe('Ann');          // 独立字面量
});

✅ 这是 GOOD 范本（tests.md 原例的变体）：经同一个 public interface 验证行为、期望值是独立字面量、读起来像 specification。实现整个换掉（换个存储、换个算法），它照样过。

4. Seam 纪律：一条三段闭环

/to-spec 与你约定 seam（理想数量是一，尽可能高）→ /tdd 只在约定的 seam 写测试（"No test is written at an unconfirmed seam"）→ /code-review 检查没人绕过约定。 两端都过同一份文档——所以 seam 对话必须在 spec 阶段认真完成。

这也是上一课 "interface 即 test surface" 的落地：想测到 interface 之外 = 模块形状不对。 当 interface 本身的形状成为问题，tdd 会调 /codebase-design 取词汇——它是参考，不是要跑的 session。

5. 检验一下

1. 红绿循环里"green"的实现应该写多少？

✅ "先写失败测试，再写恰好够让它通过的代码；不为未来的测试 anticipation、不加投机功能。"过剩的实现和测试一样，都是锁死想象的东西。

2. "重构时行为没变、测试却红了"是哪个反模式的征兆？

✅ 实现耦合的标志性征兆：测试耦合了实现细节（mock 内部、旁路验证），实现一换测试就碎。好测试的判据是"代码可以整个换掉，测试不该跟着变"。

3. tautological 测试为什么永远抓不到 bug？

✅ 期望值用和实现相同的运算得出——代码错，期望值跟着错，测试构造上必然通过。修法：期望值来自独立 truth（字面量、worked example、spec）。

4. mocking 的边界规则是什么？

✅ 只在系统边界 mock：外部 API（支付、邮件）、时间、随机性；绝不 mock 自己的类/模块/内部 collaborator。配套偏好：SDK 式接口而非通用 fetcher（每个外部操作一个具体函数，每个 mock 只返回一种 shape）。

6. 收尾

推荐的首要资料 tdd 的 SKILL.md 和同目录的 tests.md（GOOD/BAD 对照表，练习 2 和 5 都来自那里）、mocking.md（边界规则全文）。 三个文件加起来不到十分钟，是这三条纪律的唯一权威来源。
有任何不清楚的？直接问你的 agent 比如："拿我项目里最重的三个测试文件，陪我逐个过一遍三大反模式"、 "SDK 式接口和通用 fetcher 的对照例子给我看看"、"为什么 refactor 步骤被移除了？"。 也可以在下次构建时观察 /implement 驱动的 tdd 是怎么一次只走一个 slice 的。
