Lesson 0006 · 约 12 分钟

code-review：为什么评审必须拆成两根轴

前置：0005 tdd 三大反模式 ｜ 配套阅读：04 · code-review 节 · 速查表 ｜ 下一课：待定（告诉我想深入哪块）

本课的目标（一个 Win） 读完这页，你能说清 Standards 轴和 Spec 轴各查什么、为什么必须跑在互相隔离的子代理里、 为什么报告永不合并——并且能认出 4 个最常见的 Fowler smell。

0. 热身：先回忆上一课（检索练习）

不翻回去，凭记忆答。答错正好暴露要补的洞。

热身 1：期望值的健康来源是哪一个？

✅ 三种健康出处：已知正确的字面量、worked example（手算例子）、spec 条款。复跑逻辑和快照都不独立——"批改不能拿学生自己的答案当标准答案"。

热身 2："实现整个换掉（行为不变），它还绿吗？"检测哪个反模式？

✅ 这是实现耦合（伸进内部）的判据。期望值来源 → 同义反复；批量预写 → 水平切片。

1. 它在链条里的位置

/implement 每张票完成后调它；/implement-spec 在全部票合并完后对 integration branch 只跑一次（中途跑会把没建的票读成失败，触发 build-review-build 死循环—— 上上课的真实案例）。评审对象是 git diff <fixed-point>...HEAD——注意三点： 从 merge-base 度量，避免分叉噪音。

2. 两根轴各查什么

Standards 轴（规矩对不对）

primary source：仓库自己的文档——CODING_STANDARDS.md、CONTRIBUTING.md 等"代码该怎么写"的文件。

其上永远携带 smell baseline：Fowler《Refactoring》ch.3 的 12 个 code smells（仓库什么都没文档化时也适用）。

两条铁律：仓库优先、永远是 judgement call。

Spec 轴（东西对不对）

primary source：源头 issue/spec——commit 里的 issue 引用 → 用户传的 path → spec 文件 → 问用户。

找不到就跳过并报告 "no spec available"——绝不从代码反推需求。

上一课的闭环终点：它还检查"只在约定的 seam 写了测试"。

3. 为什么要隔离（本课的核心）

"一个改动可以通过一轴而挂掉另一轴"：每条标准都对、却实现了错误的东西（Standards 过 Spec 挂）； 精确做了 issue 要求的事、却破坏项目约定（Spec 过 Standards 挂）。 混合裁定会让通过的一轴掩盖挂掉的那轴。
  • 两个并行 sub-agent：两轴推理互不污染 context。金句："同一 context 评审自己不是评审，是带 slash command 的确认偏误。"
  • 报告并排呈现、永不合并或重排：分离的全部意义就是防止一轴遮蔽另一轴。
  • sub-agent 输出 400 词上限 + 每个 finding 强制引用代码位置："sub-agent 输出是 hypothesis 不是 evidence"——引用让你能逐条核验。
  • 已知边界（docs 诚实写的）：无收敛保证——"把它当线索清单处理，别跑到它干净为止（永远不会）"。

4. 12 个 Fowler smells 速览

Standards 轴的基线。完整 12 个：神秘命名、重复代码、依恋情结、数据泥团、 基本类型偏执、重复开关、霰弹式修改、发散式变化、夸夸其谈通用性、 消息链、中间人、被拒绝的遗赠。每个都配"是什么 → 怎么修"，且仓库文档明确认可的，抑制对应 smell （本地约定赢了通用基线）。

下面练最常见的四个。

5. Smell 识别三连练

练习 1：

function createOrder(customer, email, phone, address) {...}
function notify(customer, email, phone, address) {...}
function invoice(customer, email, phone, address) {...}
// 同一组参数到处结伴出现

✅ Data Clumps：总是一起出现的一坨参数，说明它们本是一个概念（Recipient/Contact）——收成一个类型，签名和调用点一起变干净。

练习 2：

// 同一个 switch 在 5 个文件里重复出现
switch (user.role) {
  case 'admin': ...
  case 'editor': ...
}

✅ Repeated Switches：按类型分派的知识散落多处，加一个 role 要改 5 个文件——和"霰弹式修改"（一改就到处开枪）互为因果。修法通常是多态或查表，把分派收进一处。

练习 3：

order.getCustomer().getAccount()
    .getBilling().charge(99);

✅ Message Chains：caller 沿着一串对象摸进别人的内部关系——它和第 4 课的深模块词汇直接挂钩：知道这条链 = 知道太多 interface。修法是把"向 Billing 收费"变成 order 身上的一个入口。

6. 和 /retro 是一对

retro 复盘 session 后提出的环境改进，喂养的正是 Standards 轴： "Mechanical mistakes become deterministic checks; judgement calls become coding standards" （机械错误变成确定性检查，判断题变成 CODING_STANDARDS.md 规则）。 而规则放哪也有讲究——"the review agent should be responsible for imposing coding standards"： 实现 agent 的 context 压力最大，review agent 只拿 diff、有空间执法。 下次构建从更好的环境开始，这就是主线的闭环。

7. 检验一下

1. 为什么要拆成两根轴？

✅ 混合裁定会让通过的一轴掩盖挂掉的那轴；隔离 + 并排呈现是防遮蔽的全部意义（顺带防"同 context 评审自己"的确认偏误）。

2. Standards 轴的 primary source 是什么？

✅ 仓库自己的 CODING_STANDARDS.md 等 + 永远携带的 Fowler 12 smells。"通用评审 skill 不知道你的标准"——工单是 Spec 轴的 source。

3. 仓库文档化标准和 Fowler smell 冲突时怎么办？

✅ "仓库优先"：文档化标准明确认可的，抑制对应 smell——尊重刻意为之的本地约定，这是它和通用 linter 的本质区别。

4. 找不到 spec 来源时，Spec 轴怎么办？

✅ 报告 "no spec available" 并只跑 Standards 轴——"绝不从代码反推需求"：把实现读成需求，等于拿学生答案当标准答案（和 tautological 测试同构的病）。

8. 收尾

推荐的首要资料 code-review 的 SKILL.md ——五步流程和两轴 brief 的原文。想深挖 smells 就读 Fowler《Refactoring》第 3 章 （Standards 轴的 baseline 出处，每个 smell 配"是什么 → 怎么修"）。
有任何不清楚的？直接问你的 agent 比如："拿我最近一次 commit，按两轴给我各出一份报告"、"12 个 smells 里剩下 8 个各是什么？"、 "为什么 implement-spec 中途跑 code-review 会死循环？"——或者在你自己的分支上真的跑一次 /code-review，对照本课看两份报告是不是真的并排、不合并。
