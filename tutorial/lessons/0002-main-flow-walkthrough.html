Lesson 0002 · 约 10 分钟

主线工作流走查：从想法到上线

前置：0001 调用类型与失败模式 ｜ 配套阅读：07 工作流组合 · 速查表 ｜ 下一课：grilling 实操演练

本课的目标（一个 Win） 给你一个真实的功能想法，你能自己写出该敲的命令序列，并在每个岔路口说出为什么走这边。 这是使用这套 skill 最常用的一天到一天的路径。

1. 主线全景（五步）

  1. 1/grill-with-docs — 拷问式对齐 agent 一轮轮问你（每题带推荐答案），术语当场写进 GLOSSARY.md，难逆决策写成 ADR。每次要改东西前都从这里开始。
  2. 2/handoff → /prototype → /handoff — 绕道（仅当需要） 遇到"跑起来才能回答"的问题（状态机对不对？UI 该长啥样？）才走这条路：交接出去 → 做可抛弃原型 → 把答案带回来。
  3. 3/to-spec → /to-tickets — 固化决策（仅多 session 工程） spec 是决策存档（含与你确认的测试 seam）；工单是垂直切片 + 阻塞边。小改动跳过这步，直接第 4 步。
  4. 4/implement 或 /implement-spec — 构建 构建内部自动驱动 /tdd（只在约定 seam 写测试），收尾自动跑 /code-review（双轴）。逐票手推或整图并行，二选一。
  5. 5/pr → /retro — 上线与复盘 PR body 自动套三段模板（视图/证据/风险判定）；retro 复盘的是环境：机械错误变检查，判断题变标准。

2. 两个岔路口

岔路 A：这个问题聊得明白吗？

grilling 时如果卡在"one long form or three pages?"这类纸上谈不明白的问题，硬聊只会越拖越长。 判据：答案是实物反应（状态、逻辑、看得见的 UI）→ 绕道 prototype； 答案在你自己脑袋里 → 继续 grilling； 答案在别人脑袋里 → /to-questionnaire； 答案在外部世界（文档、API）→ /research 后台查。

岔路 B：这活儿跨几个 session？

规模路径
一次对话装得下grill 完直接 /implement（同窗口）
多张工单、你想逐票掌控/to-spec → /to-tickets，然后逐票 /implement，票间 /clear
多张工单、你想一次跑完/to-spec → /to-tickets → /implement-spec（frontier 并行 + worktree 隔离）
大到一个 session 连规划都装不下/wayfinder 绘决策地图，雾散后再回到 /to-spec

3. 上下文卫生（最容易踩的坑）

第 1–3 步（拷问 → spec → 工单）保持在一个不间断的 context window 里—— spec 和工单要建立在拷问产生的同一份思考上。到 /to-tickets 为止都不要 compact/clear。

为什么：spec 是"决策存档"，但它合成自对话；窗口断了，agent 只能从 tracker 回读 spec，细节会丢。 之后每张工单自包含，所以逐票 /implement 中间随便 /clear。 判断窗口还能不能用的标准是 smart zone（约 150k token 内模型仍在敏锐推理）： 逼近上限时别硬撑（"don't push on degraded"），在最近的阶段边界做处置。

4. 场景演练（本课的 Win）

场景：你维护一个 Next.js SaaS，想加"用户可以把自己建的仪表盘分享给队友"功能。你估计要动数据库、 API、权限系统和前端，大概两周的活。你现在脑子里只有个模糊想法。

先自己写：你会按什么顺序敲哪些命令？（写在纸上或输入框里都行）

写完了？点开对照参考答案
  1. 1/grill-with-docs 两周的活肯定跨 session → 走完整主线。"分享"的语义（只读？可编辑？链接有效期？）会被问出来；"Shareable Dashboard"、"Seat" 等术语进 GLOSSARY。
  2. 2/handoff → /prototype → /handoff 如果对"权限级联"（移除队友时他分享出去的链接怎么办？）想不清楚——做个单 HTML 状态机原型，自己乱按找漏洞。
  3. 3/to-spec 合成 spec；和你确认一个测试 seam（大概率是分享 API 的 public 接口）。
  4. 4/to-tickets 垂直切片：①分享链接生成 + ②只读渲染 + ③权限校验 + ④撤销……每片独立可 demo；quiz 批准粒度和阻塞边。
  5. 5/implement-spec（或逐票 /implement） 四张票无依赖冲突的话整图并行最快；最后自动跑一次 code-review。
  6. 6/pr → /retro PR：组件树视图 + before/after 截图 + "two-way door"判定（分享可撤销，可回）。retro：这次哪里反复卡住？该加什么检查？

对照时重点看：岔路 A、B 你选对了吗？第 3 步的 seam 想到了吗？

5. 检验一下

1. 主线第 1-3 步（拷问→spec→工单）应如何处理上下文？

✅ spec 和工单要建立在拷问产生的同一份思考上，到 /to-tickets 为止不要 compact/clear。之后的工单自包含，票间随便 /clear。

2. /to-tickets 拆工单的正确方式是什么？

✅ 曳光弹 = 垂直切片：每片窄但完整穿过每一层（schema、API、UI、tests），完成的片独立可 demo。判别法："问每张票：完成后我能 demo 什么？答不出就是横切。"

3. implement 与 implement-spec 的关键区别是？

✅ implement 是你逐票手推（票间 /clear）；implement-spec 把工单当 task graph，在 ready frontier 上并行派 implementer subagent（各自 worktree + /tdd），最后对 integration branch 跑一次 code-review。两者都用 tdd 和 code-review。

4. code-review 在 implement-spec 里什么时候跑？

✅ 它对照整个 spec 审查——中途跑会把没建的票全读成失败，触发"build-review-build"死循环（真实案例：五票 feature 的循环跑了四小时）。

6. 收尾

推荐的首要资料 ask-matt 的 SKILL.md ——作者本人手写的主线路由图，本课的每个岔路口它都有一句话裁决。以后忘了流程，跑 /ask-matt 就行。
有任何不清楚的？直接问你的 agent 比如："拿我现在的项目，帮我把某个功能走一遍这条主线"、"implement-spec 的 worktree 是怎么隔离的"、 "什么时候该用 wayfinder 而不是 to-spec？"。也可以直接说 下一课，我会为你准备 grilling 实操演练。
