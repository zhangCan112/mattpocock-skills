retro：复盘环境，不复盘代码

前置：0007 wayfinder 决策地图（本课顺带补讲 0006 的洞）｜ 配套阅读：03 · retro 节 · 速查表 ｜ 下一课：待定（告诉我想深入哪块）

本课的目标（一个 Win） 读完结这页，你能说清 retro 的七个类别各把修复落在哪里，并且拿到 session 里任何一个挣扎时刻， 能判断它该变成 check、pointer 还是 standard——以及为什么"往 AGENTS.md 加一行"几乎总是错的。

0. 热身：先回忆上一课（检索练习）

不翻回去，凭记忆答。答错正好暴露要补的洞。

热身 1：wayfinder 和 grill-with-docs 的分界线是什么？

✅ session 数，不是项目大小：装得下就 grill（更便宜更好），装不下才建图。绿地也不是必要条件——legacy 代码库上"这里已经什么是真的"本身就是雾。

热身 2："支付用 Stripe 还是自建？——问题一句话说得清，但要等'目标市场'那张票先定。"这条该进哪一格？

✅ fog vs ticket 的判据是"现在能不能把问题说 sharp"，不是"现在能不能回答"。已 sharp 但被阻塞 → 照样开票，blocking 边排在后面。

1. 它在链条里的位置：最后一步

grill-with-docs → to-spec → to-tickets → implement → code-review → retro

主线走到头，retro 回头读一个 coding session 的记录（默认当前 session——挣扎还在 context window 里， 是最佳情形；session 太长就 clear，让新的 /retro 指向旧 session 的 log）， 找出 agent 挣扎的时刻，然后提议改进 agent 的 environment。

  • 改环境，不改代码：bug 发出去了、找一个文件花了二十次 tool call、reviewer 漏了规矩——它都不直接修。它问的是：仓库里的什么东西让这些事发生了？
  • 只提议，不动手：按严重度从高到低列候选，你挑了才落地。这是刻意的——有用户被"自动装上、拦截好改动"的 auto-hooks 坑过。user-invoked，模型不会自己想到跑它。
  • 时机：session 比它应有的更艰难之后。顺畅的 session 没什么可教，每次都跑只会"生产没人需要的规则"。

和邻居的分界：code-review 评代码（这次产出对不对）；improve-codebase-architecture 只要代码就能跑、改代码结构；retro 要 session 历史、改环境。三者互补，谁也不替代谁。

2. 四步流程

  1. 先调 writing-for-agents 拿写作风格——它提议的每个 steering 文件都得按元规范写；
  2. 读 primary sources：用户指定的 session，或当前 session 的记录；
  3. 按七个类别找候选（下一节）；
  4. 按严重度从高到低呈现，停手等人类挑选。

3. 七个类别：出了什么事 → 修在哪

Session 里出了什么修复落点
找文件/事实花太久Navigation pointer（从它已经在读的文件指过去）
犯了工具本可抓住的错Automated check：lint 规则 / 类型 / 测试 / pre-commit / CI
Reviewer 漏了 judgement callCODING_STANDARDS.md 加规则（给 reviewer 读）
AGENTS.md 太大把 steering 搬出去，进 standards 或 checks
某次 tool call 又贵又没用精简或替换工具
steering 文件里有不改行为的行删 no-op
关键信息 agent 够不着扩访问：tee dev server 日志、第三方 readonly

三个类别埋着深一层的纪律：

  • Automated checks——先读仓库已有的。发明新 check 之前，先读仓库自己的 check 命令（package.json 的 lint/check scripts、CI workflow）。一个已存在但没接线、或悄悄坏掉的 check，本身就是 finding——接线，不是重建。更狠的：仓库完全没有 guardrail（既无 pre-commit 也没有 CI 跑 lint/typecheck/test）这件事本身就是一个 finding——"an un-linted repo is a standing missed opportunity, not a neutral default"。
  • Coding standards——落笔之前先分类。violation 分两型：mechanical（固定语法模式、banned API、import 形状、文件位置规则）→ deterministic check，句号——"a check can fail and a sentence in a standards file can't"（check 会红，standards 文件里的一句话永远不会）。只有真正的 judgement call（跨文件一致性、"跟周围风格匹配"，任何 guardrail 都替代不了的）才配写成 prose。"Default to building the check over writing the rule."
  • Global AGENTS.md——搬运，不是增删。这个类别专找"住在 AGENTS.md 里、本该住在 standards 或 check 里的 steering"。

4. 两条核心设计思想

① 标准属于 reviewer，不属于 implementer

所有工作分两段：implementation agent 的 context 压力最大——探索、写码、调试全压在它身上； review agent 压力最小——只拿一个 diff。所以新规则要放有空间执行它的地方：review。 这正是 0006 埋的伏笔兑现处：retro 是 Standards 轴的喂养者 ——"机械错误变成确定性检查，判断题变成 coding standards"，下次构建从更好的环境开始，主线闭环闭在这里。

② "往 AGENTS.md 加一行"几乎总是错误的修复位置

docs 里被问最多的问题就是它（"The agent keeps making the same mistake. Should I add a line to CLAUDE.md?"——"Usually not"）。三条理由：那行字无条件加载进之后的每个 session （十个 session 只有一个用得上，另外九个都在付利息）；它稀释文件里其他内容的权重； 它随代码演化悄悄过期。AGENTS.md 只该放 navigation pointers。 同理，retro 不是 memory system——它不记录发生了什么，它改环境让错误不可能再发生。

文件角色速查：CLAUDE.md/AGENTS.md 极度节制、只放 pointer；CODING_STANDARDS.md review 时读、不是 implement 时读，超 1000 行就往 docs 加 pointer；先找已有 docs 再写新的。

5. docs 页诚实记录的弱点

  • 不会自己清理自己：它只看一个 session，看不到"上个月提议的 lint 规则现在是否在好代码上疯狂误报"。check 的 pruning 永远是你的活——"A rule that fires constantly on good code is the sign to remove it."
  • 最强批评：编造 generic advice 填类别。用户原话："工作一结束，AI 倾向忘掉 session 中间的挣扎，转而编造通用建议来满足 retro 的类别。"防线一条：每个候选必须指回 session 里的一个具体时刻——指不回去的直接丢弃；严重度排序也只当初稿（安静但昂贵的错，可能排在聒噪但便宜的错下面）。
  • 提议的 check 也是代码：先在仓库上试跑，再让它拦 merge。

6. 实操：这个挣扎该变成什么？

五个时刻全来自同一个艰难 session。每题选出修复落点。

练习 1：agent 三处 import 了 moment，仓库其实早定了 dayjs，reviewer 也没拦住。

✅ banned API = mechanical（固定语法模式）→ deterministic check，句号。"a check can fail and a sentence in a standards file can't"。AGENTS.md 那行还会进每个 session 付利息。

练习 2：agent 花 18 次 tool call 才找到真正生效的 env override 文件（藏在 packages/app 里，README 只字未提）。

✅ 找信息费劲 = Navigation 类别：从它已经在读的文件（README、package.json）里加一行 navigation pointer，指向藏起来的事实。十八次 tool call 下次变一次。

练习 3：错误处理风格分裂——有的 early return、有的三层嵌套 if。reviewer 该管，但没有 linter 写得出这条规则。

✅ 真正的 judgement call（"跟周围风格一致"，任何 guardrail 都替代不了）才配写成 prose；且 CODING_STANDARDS.md 是 review 时读、不是 implement 时读——规则放在有空间执行它的地方。

练习 4：agent 干耗半小时调试，因为 dev server 的报错只打在人类终端里，它根本看不见。

✅ 关键信息够不着 = Information access：tee dev server 日志到文件、给第三方服务 readonly。信息给到了，挣扎直接消失——不需要任何"规则"。

练习 5：AGENTS.md 里躺着一行 "Be careful with the auth module"——no-op 测试做过，agent 行为从没因它改变。

✅ no-op 测试：删掉这行，行为变吗？不变 → 删整句（不是修剪措辞）。对已经读过一切的读者，模糊告诫是空转；具体危险要么写成 check，要么写成具体规则。

7. 检验一下

1. retro 改进的对象是什么？

✅ 改环境、不改代码、只提议、不动手。代码质量找 code-review；代码结构找 improve-codebase-architecture（它只要代码，retro 要 session 历史）。

2. mechanical 违规（比如 banned API）的修复落点是？

✅ "a check can fail and a sentence in a standards file can't"。prose 只留给 linter 永远顶不上的 judgement call。

3. 为什么编码标准由 review agent 来执法？（0006 补讲：你热身错的正是这个原理）

✅ implementer 探索+写码+调试，context 压力最大；reviewer 只拿一个 diff。规则放在有空间执行它的地方——和 0006 两轴隔离是同一条原理：裁定要分开、且各有干净的 context。

4. "agent 反复犯同一个错，往 AGENTS.md 加一行规则"——哪句评价对？

✅ 那行字无条件进每个 session（十个里九个付利息）、稀释其他内容、随代码过期。AGENTS.md 只放 navigation pointers；mechanical → check，judgement → standards。

8. 收尾

推荐的首要资料 retro 的 SKILL.md ——四步流程、七类别原文（每个类别自带 _Use when_ 触发条件）和文件角色 Reference 节。 真实失败与边界（不清理自己、编造 generic advice、只提议的由来）都在 docs 页的 Common questions。
有任何不清楚的？直接问你的 agent 比如："拿我们这个教学 session 跑一次 retro 演练——我 0006/0007 热身答错这件事，环境该改什么？"、 "检查我某个仓库有没有 guardrail：pre-commit 和 CI 各跑了什么？"、 "把我 AGENTS.md 逐行做 no-op 测试"——或者在一个艰难 session 结束后真的跑一次 /retro，对照本课看候选是不是每条都能指回具体时刻。
