# 01 全景图：这个仓库是什么

> 本文来源：[README.md](../README.md)、[CLAUDE.md](../CLAUDE.md)、[ask-matt 路由图](../skills/engineering/ask-matt/SKILL.md)

## 一句话定位

**mattpocock/skills** 是 Matt Pocock（Total TypeScript / AI Hero 作者）日常真实使用的 agent skills 集合。它的口号是 **"Skills For Real Engineers"（给真正的工程师的技能）**：目标是做真正的工程，而不是 "vibe coding"（凭感觉写码）。

## 它反对什么

README 开篇点名了几个流行的 "流程全家桶" 方案：**GSD、BMAD、Spec-Kit**。这些方案试图通过"接管整个流程"来帮你，但代价是：

- 夺走你的控制权（你必须按它的流程走）
- 流程本身出 bug 时很难排查

所以本仓库的立場是三条设计承诺：

1. **小**（small）—— 每个 skill 只做一件事
2. **易改**（easy to adapt）—— 鼓励你 fork 和魔改（"Hack around with them. Make them your own."）
3. **可组合**（composable）—— 像 Unix 小工具一样拼接成工作流

## 四大失败模式：整个仓库存在的理由

README 用四章 "Why These Skills Exist" 解释了 agent 编码的四种常见失败，每一种都对应一组 skill 作为解药。理解这四点，就理解了整个仓库的地图。

### 失败模式 #1：Agent 没做我想要的（对齐失败）

> "No-one knows exactly what they want"（没人能完全说清自己要什么），《The Pragmatic Programmer》

**症状**：你以为 agent 听懂了，结果它做出来的东西完全不是你想的。这是软件开发中最古老的失败（人类开发者也一样），在 AI 时代只是换了形式。

**解药**：**Grilling（拷问式访谈）**——在动手之前，让 agent 反过来对你展开详细盘问，把需求的每个分支都问清楚。

- [`/grill-me`](https://github.com/mattpocock/skills)（productivity）：非代码场景的拷问
- [`/grill-with-docs`](../skills/engineering/grill-with-docs/SKILL.md)（engineering）：拷问 + 沉淀领域文档

这两个是全仓库最流行的 skill。作者建议：**每次要动手改东西之前都用**。

### 失败模式 #2：Agent 太啰嗦（语言不共享）

> 引用自 Eric Evans《Domain-Driven Design》：有了统一语言（ubiquitous language），开发者之间的对话和代码表达都源自同一个领域模型。

**症状**：agent 被丢进项目里自己猜行话，结果用 20 个词表达 1 个词能说清的概念。

**解药**：**共享语言（shared language）**——一份帮 agent 解码项目行话的文档（`GLOSSARY.md`）。README 给了个真实例子：

- 改善前："课程里某小节的一节课在'实体化'（即在文件系统中获得位置）时出了问题"
- 改善后：**"materialization cascade（实体化级联）出了问题"**

一个术语压掉一整句话，而且收益是复利的：变量/函数/文件命名一致 → 代码库更好导航 → agent 思考消耗的 token 更少。

这项能力内建在 `/grill-with-docs` 中，底层由 `/domain-modeling` 驱动。作者称这可能是**整个仓库最酷的技术**。

### 失败模式 #3：代码跑不起来（反馈回路缺失）

> "Always take small, deliberate steps. The rate of feedback is your speed limit."（反馈速率就是你的速度上限），《The Pragmatic Programmer》

**症状**：你们明明对齐了，agent 产出的代码还是垃圾。因为 agent 对"代码实际能不能跑"是盲的。

**解药**：**反馈回路**——静态类型、浏览器访问、自动化测试。

- [`/tdd`](../skills/engineering/tdd/SKILL.md)：红-绿-重构循环，先写失败的测试再写实现
- [`/diagnosing-bugs`](../skills/engineering/diagnosing-bugs/SKILL.md)：把调试最佳实践包成一个分阶段、有门控的纪律循环

### 失败模式 #4：我们造了一个大泥球（设计腐化）

> "Invest in the design of the system every day."（每天都要投资系统设计），Kent Beck《Extreme Programming Explained》
>
> "最好的模块是深的：大量功能藏在简单接口后面。" John Ousterhout《A Philosophy of Software Design》

**症状**：agent 极大加速了写码，也就同样加速了软件熵增。用 agent 写出来的代码库复杂度以前所未有的速度膨胀。

**解药**：**关心代码设计**——这不是一句口号，被落实到了仓库的每一层：

- [`/to-spec`](../skills/engineering/to-spec/SKILL.md)：写 spec 前先拷问你将触碰哪些模块
- [`/improve-codebase-architecture`](../skills/engineering/improve-codebase-architecture/SKILL.md)：扫描代码库寻找"深化机会"（deepening opportunities），每隔几天跑一次

## 仓库的目录组织（buckets）

```
skills/
├── engineering/    # 日常代码工作（21 个，主推）
├── productivity/   # 日常非代码工作流（7 个，主推）
├── misc/           # 留着但很少用，不进插件（4 个，已冻结）
├── in-progress/    # beta：故意公开求反馈，不进插件（7 个）
└── deprecated/     # 已废弃
```

规则（见 [CLAUDE.md](../CLAUDE.md)）：

- **主推（promoted）** = `engineering/` + `productivity/`。必须出现在顶层 README，且登记进 Claude 插件清单 `.claude-plugin/plugin.json`
- 每个主推 skill 配一个面向人类的文档页 `docs/<bucket>/<skill-name>.md`，固定四段：**What it does / When to reach for it / Common questions / It's working if**
- 非主推的 skill 不进 README、不进插件、没有文档页
- 这个仓库**不接受新 skill 提案**（见 [SCOPE.md](../SCOPE.md)）：能用现有 skill 组合出来的行为，就不配拥有新 skill。"目录越小越少，保持正确的成本就越低。"

## 主线工作流（先睹为快）

`ask-matt`（仓库自带的路由器）把主推 skill 串成一张图。核心主干是 **idea → ship（想法 → 上线）**：

```
/grill-with-docs        拷问式对齐 + 沉淀术语表
      │
      ├─（设计问题难落地？）→ /handoff → /prototype → /handoff
      │
      ▼
/to-spec                把对话压缩成 spec，发到 issue tracker
      ▼
/to-tickets             拆成 tracer-bullet 工单，声明阻塞关系
      ▼
/implement  或  /implement-spec     逐工单实现（内部驱动 /tdd）
      ▼                                    │
      ▼                                     ▼
/pr  ←  /code-review    双轴评审（Standards + Spec）
      ▼
/retro                  复盘：改进 agent 的环境，让下次更好
```

三条"匝道"汇入主线：

- **Bug 和需求堆积** → `/triage`（分诊状态机）
- **东西坏了** → `/diagnosing-bugs`（诊断循环）
- **超大迷雾工程** → `/wayfinder`（决策工单地图）

详见 [07-工作流组合.md](./07-工作流组合.md)。
