# 07 工作流组合：从想法到上线

> 本文来源：[ask-matt 路由图](../skills/engineering/ask-matt/SKILL.md)、[PHASE-BOUNDARIES.md](../skills/engineering/ask-matt/PHASE-BOUNDARIES.md)

```
                    │  ③ 跨多 session 构建？               │
                    │                                     │
                    │  是 → /to-spec（合成 spec+约定seam） │
                    │        → /to-tickets（曳光弹+阻塞边）│

                    ④ /pr（PR body 塑形，model-invoked 自动套用）
                                   ▼

```

**上下文卫生（context hygiene）**：第 1–3 步保持在**一个不间断的 context window** 里（拷问、spec、工单要建立在同一份思考上，`/to-tickets` 之前不要 compact/clear）。每张票是自包含的，所以 `/implement` 逐票跑、票间 `/clear`、上下文用完即弃。判据是 **smart zone**（约 150k token 内模型仍在敏锐推理）——逼近上限时"don't push on degraded"，在最近的阶段边界处置。

## 三条匝道（On-ramps）

| 起点 | 入口 | 汇入点 |
|---|---|---|
| Bug 和外部需求堆积 | `/triage`（分诊状态机） | 产出 `ready-for-agent` 的票 → `/implement` |
| 东西坏了（难缠 bug） | `/diagnosing-bugs`（六阶段门控循环） | 修完同 session 跑 `/retro`；无 seam 锁定 → `/improve-codebase-architecture` |
| 超大迷雾工程（一个 session 装不下） | `/wayfinder`（决策票地图） | 地图清空 → `/to-spec #<map_issue>` 汇入主线 |

**注意**：triage 只处理**外来** issue；`/to-tickets` 的产物天然 agent-ready，不要 triage 它们。两条车道（外来工作走 triage、自发工作走 spec flow）只在 `ready-for-agent` 标签处汇合。

## 日常养护（Codebase health）

`/improve-codebase-architecture`：有空就跑，扫描深化机会 → HTML 报告 → 你挑一个 → 内部走 grilling。**它是 survey 不是 rescue**，产出是一个 idea，带回主流程 `/grill-with-docs` 重新开始。与 `/codebase-design` 分工：前者**找** module，后者是**设计**它的工作台。

## 词汇层（Vocabulary underneath）

两个 model-invoked 词汇表在所有 skill 底下运行：
- `/domain-modeling`：项目**领域**语言（GLOSSARY.md + ADR）
- `/codebase-design`：**模块形状**语言（module/interface/depth/seam/leverage/locality）

## 阶段边界决策树

一个 session 内的阶段（grilling、实现、QA）之间，五个选项**按序**问，第一个 yes 生效：

```
1. 能继续吗？      下一阶段需要本阶段作为 primary source？
                  或 smart zone 还够？ ── 是 → Continue（成本为零，先排除它）
2. 上下文无关吗？   探索、决策、死胡同全都可弃？ ── 是 → /clear（最便宜的棋）
3. 需要移交吗？     换 harness / 换目录 / 给同事 / 中途分叉支线 ── 是 → /handoff
4. 能 AFK 吗？      任务 scoped 到无人值守也能跑？ ── 是 → Subagent
5. 都不是 → /compact（兜底默认，不是第一反应）
```

**背后的经济学**：除 Continue 外每一步都把 primary source（逐字发生的会话）变成 secondary source（有损摘要）——信息全/噪声多/余地小 ↔ 有损/噪声少/余地大。从 compact 开始的人会得到一个"自信但错"的新会话。

## 完整调用关系图

```
用户敲的命令                      内部调用的积木（model-invoked）
─────────────                    ────────────────────────────
/grill-with-docs        ──────→  grilling + domain-modeling
/grill-me               ──────→  grilling
/triage                 ──┐
                          ├────→  grilling + domain-modeling（按需）
/wayfinder              ──┤
                          ├────→  research（research 票）
                          ├────→  prototype（prototype 票）
                          └────→  grilling + domain-modeling（grilling 票）
/improve-codebase-arch  ──────→  codebase-design → grilling + domain-modeling
/implement              ──────→  tdd → code-review
/implement-spec         ──────→  tdd（每个 implementer）→ code-review（最后）
/retro                  ──────→  writing-for-agents
                                  （tdd 又按需调 codebase-design）
/prototype /research /diagnosing-bugs /pr /wizard /writing-for-agents
                                  ← 独立积木，agent 自主够到
/ask-matt /to-spec /to-tickets /setup-matt-pocock-skills
                                  ← 不调用任何 skill（路由/合成/配置）
/handoff /teach /to-questionnaire /wait-what
                                  ← 独立 productivity 工具
```

**一个不变式贯穿全图**：user-invoked 之间绝不互调。链条的每一环由用户驱动——这正是设计意图：**人是流程的所有者，agent 是纪律的执行者。**

## 一次完整旅程（示例走查）

假设你要给 SaaS 产品加一个"团队工作区"功能：

1. **`/setup-matt-pocock-skills`**（一次性）：告诉它用 GitHub Issues、保留五个 canonical triage 标签、单 context 域文档
2. **`/grill-with-docs`**：它一轮轮问你（每题带推荐答案），同时把 "Workspace"、"Seat"（席位）这些术语写进 GLOSSARY.md；"为什么不用多租户行级隔离"过三道门写成 ADR-0004
3. 聊到"邀请流程的状态机"时你不确定——**`/handoff`** 出去，新会话 **`/prototype`** 做一个单 HTML 的 state machine demo，你自己乱按按钮发现 "pending invite 被撤销后还能接受"——想法里的 bug！答案 **`/handoff`** 带回来
4. 规模判断：这是三个月的工程，还看不清路——**`/wayfinder`** 绘图：destination 写在 map issue 上，前端 6 张票是雾；并行点火 2 张 research 票（查各竞品的席位模型）；一次解决一张决策票
5. 雾散了——**`/to-spec #<map_issue>`** 把决策 collapse 成 spec，其中和你确认了**唯一一个测试 seam**（Workspace 的 public API）；**`/to-tickets`** 拆成 14 张曳光弹票 + 1 张 prefactor 票，quiz 你批准粒度和阻塞边
6. **`/implement-spec`**：frontier 上 3 张票并行，各自在 worktree 里跑 **`/tdd`**（红绿循环、只在约定的 seam 写测试），逐个 fast-forward 合并进 integration branch；最后跑一次 **`/code-review`**（Standards 轴对照 CODING_STANDARDS.md + Fowler smells，Spec 轴对照 spec）
7. **`/pr`**：Summary 用 component tree 视图、Evidence 放 before/after 截图、Merge Danger 判 "two-way door, medium blast radius"
8. **`/retro`**：这次 session 里你三次纠正它把 "workspace" 写成 "organization"——它提议把术语对照写进 CODING_STANDARDS.md 供 review agent 执法；它还发现 repo 没有 pre-commit hook——"an un-linted repo is a standing missed opportunity"

下次构建从一个更好的环境开始。这就是闭环。

## 阅读 / 使用建议

- **第一次上手**：装好后先跑 `/ask-matt` 描述你的情境，让它告诉你敲什么
- **每天**：任何改动前 `/grill-with-docs`；有空跑 `/improve-codebase-architecture`
- **深读**：每个 skill 的文档页在 `docs/<bucket>/<skill>.md`，固定四段（What it does / When to reach for it / Common questions / It's working if），docs 里还诚实记录了每个 skill 的已知缺陷与演进史——本身就是好教材
