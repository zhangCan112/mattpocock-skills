# 03 Engineering 篇（上）：11 个用户调用 skill

> 本文来源：`skills/engineering/` 下 11 个 user-invoked skill 的 SKILL.md 与配套文件

这一层的 skill 只能由**你手动输入**触发（`disable-model-invocation: true`）。它们的职责是**编排**：把流程串起来，把"怎么做才对"委托给下一章的 model-invoked 纪律。规则：user-invoked 可以调用 model-invoked，但**绝不调用另一个 user-invoked**——所以主链条（grill → spec → tickets → implement → review → retro）由**你**驱动，每一步都是你敲的。

```
grill-with-docs → to-spec → to-tickets → implement / implement-spec → code-review → pr → retro
        │                                                        ↑ 链条由用户驱动 ↑
        └── 内部调用：grilling、domain-modeling、tdd、code-review 等 model-invoked 积木
```

## ask-matt — 手写的路由器

**定位**：你描述自己所处的情境，它告诉你该敲哪个（或哪串）命令，然后停下——**只推荐、不执行**。

**解决什么**：27 个 skill 里 16 个是 user-invoked，agent 的 context 里根本看不到它们（这正是 user-invoked 的定义），所以不能指望模型自动路由。它同时回答"两个相似 skill 分不清"（grill-me vs grill-with-docs vs wayfinder）和"这个 context 窗口接下来怎么办"。

**它是一张五层地图**（不是流程）：
- **主流程**（idea → ship，四个步骤，详见第 7 章）
- **On-ramps**：`/triage`（外来 issue）、`/diagnosing-bugs`（难缠 bug）、`/wayfinder`（超大迷雾工程）
- **Codebase health**：`/improve-codebase-architecture` 日常养护
- **Vocabulary underneath**：`/domain-modeling` 与 `/codebase-design` 两个词汇层
- **Standalone**：grill-me、prototype、research、teach 等

**为什么这样设计**：
- **推荐后即停**："what you get back is the next thing to type, and you type it"——保持人在环上
- **散文而非清单**：prose 承载条件分支（"是否有 codebase、是否跨 session、问题能否靠谈解决"），静态清单会丢掉这些
- **自认是 secondary source**：文档页声明 "Where the router and a SKILL.md disagree, the SKILL.md is right"
- 第一句指令就是防御："Before stating what a skill does, read that skill's SKILL.md"（对抗 agent 用自己的一行摘要瞎编别的 skill 的行为）
- 通用路由提案三次被拒：它只认识本仓库的 skill

**调用关系**：不调用任何 skill（纯路由）。

## grill-with-docs — 拷问 + 留痕

**定位**：有状态的拷问会话。它的 SKILL.md 全部正文只有一句话：**"Call the Skill tool twice, for 'grilling' and 'domain-modeling'."**

**解决什么**：README 四大失败模式的前两个——#1 对齐失败（agent 没做我想要的）由 grilling 解决；#2 冗长（语言不共享）由 domain-modeling 的 GLOSSARY.md + ADR 解决。与无状态的 `/grill-me` 分工：**有 repo 就用它**——"leaves a paper trail, which makes it strictly the better one whenever a repo is there"。

**工作流程**（完全由两个被调用的 skill 组合而成）：
- **grilling** 提供"怎么问"：design tree → frontier → rounds（详见第 5 章）
- **domain-modeling** 提供"怎么记"：术语敲定的**瞬间** inline 写入 `GLOSSARY.md`（不攒批）；难逆决策过三道门才写 ADR

**为什么这样设计**：
- **一行 SKILL.md 的纯组合设计**：grill-with-docs 自己零流程，完全委托。收益是**原语复用**（grilling 同时服务五个入口）；代价是依赖必须同装（文档页：只装 grill-with-docs 一个是跑不起来的）
- **inline 写入的验收标准**："GLOSSARY.md changes *during* the session, term by term, rather than appearing in one lump at the end"——session 结束才补写的 glossary 只是 session 的摘要，inline 版本才是 session 的产出
- **已知留白**：大量已敲定的决策只存在于对话里——所以主流程的答案是紧接着喂给 `/to-spec`

**调用关系**：`grilling` + `domain-modeling`（双调）。

## triage — 分诊状态机

**定位**：把 issue tracker 上的**外来** issue（bug 报告、feature request、外部 PR）推过一个小型角色状态机，产出 agent-ready 的 brief、给 reporter 的追问、或带记录原因的关闭。

**解决什么**：外来工作以 reporter 留下的任意形状到达，agent 没法直接干活；半年前拒绝过的请求又来一遍还得重新吵（→ `.out-of-scope/` 知识库去重）；已实现的需求被当新需求（→ redundancy 检查按 domain concept 搜索）；不经验证就 brief（→ agent 在幻想的 bug 上空转）。

**关键边界**：**只处理"不是你创建的" issue**——`/to-tickets` 产出的票天然 agent-ready，"don't triage them"（文档页有真实案例：用户对 spec flow 的产物跑了 triage，AFK runner 全部无视）。

**角色体系**：2 个 category role（`bug` / `enhancement`）× 5 个 state role（`needs-triage` → `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`）。每个 issue **恰好一个 category + 一个 state**。所有发出的评论以 `> *This was generated by AI during triage.*` 开头。

**单个 issue 的处理**：① Gather context（读全文、解析历史 triage notes 避免重问、跑 redundancy + prior rejection 两个检查）→ ② **Recommend（等 maintainer 指示）** → ③ **Verify the claim**（bug 按步骤复现；"细节不足"本身就是 needs-info 的最强信号）→ ④ Grill（按需，调 grilling + domain-modeling）→ ⑤ Apply outcome（四种出口）。

**AGENT-BRIEF 的 brief 纪律**（"the brief is the contract"）：
- **Durability over precision**：issue 可能躺数周——禁文件路径/行号，写 interface、type、行为契约
- **Behavioral, not procedural**：写 what 不写 how
- **Explicit scope boundaries**：防 gold-plating

**为什么这样设计**：
- **为什么状态机**：exactly one state per item 让"哪些可被 AFK agent 拿走"变成一个 label 查询；刻意保持词汇最小（blocked/deferred 等最受请求的状态都没加）
- **为什么已实现的 wontfix 不写 `.out-of-scope/`**："recording it would poison the dedup checks with false rejections"
- `.out-of-scope/` 一个**概念**一个文件（不是一 issue 一文件），像短设计文档，是 institutional memory

**调用关系**：条件性调用 `grilling` + `domain-modeling`。

## improve-codebase-architecture — 深化机会普查

**定位**：扫描代码库寻找 **deepening opportunities**，以自包含 HTML 报告呈现候选，你选中一个后再进入 grilling——**它是 survey（普查），不是 rescue（救援）**，全程不改代码。

**解决什么**：README 失败模式 #4（大泥球）的日常解药。三种典型 shallowness：为可测性抽出的 pure function（bug 藏在调用方式里，无 locality）；module 跨 seam 泄漏；理解一个概念要在五个文件间弹跳。

**工作流程**（三阶段）：
1. **Explore**：**Scope before you scan**——用户没指方向就回溯 `git log` 找 hot spots（deepening 的回报在"让未来改动更容易"，没人碰的代码里永远不回本）。派 sub-agent 有机走代码库，对疑似 shallow 的东西施加 **deletion test**（删掉它是让复杂度集中还是只是挪位置？"集中"才是信号）
2. **HTML 报告**：写到 OS 临时目录（"so nothing lands in the repo"）并打开。每个候选一张卡：Files / Problem / Solution / Benefits（以 locality 与 leverage 表述）/**Before/After 双栏可视化**/推荐强度徽章（Strong / Worth exploring / Speculative）。措辞强制用 GLOSSARY + codebase-design 词汇（"the Order intake module"，不是 "FooBarHandler"）。**门控："Do NOT propose interfaces yet"**——写完就问"想探索哪个？"
3. **Grilling loop**：选定后调 `grilling` 走决策树；inline 调 `domain-modeling` 记新概念；用户以 load-bearing 理由否决候选时**提议 ADR**（"Want me to record this as an ADR so future architecture reviews don't re-suggest it?"）；要探索备选接口时再调 `codebase-design` 的 design-it-twice

**为什么这样设计**：
- **为什么不直接重构**：survey 让你可以对"还没准备好动的代码库"跑它；产出是一个 **idea**，带回主流程 `/grill-with-docs` 或 `/to-spec`
- **为什么 HTML + 临时目录**：before/after 图承载论证重量，纯 prose 说不清"哪个浅、怎么变深"；临时目录保证 repo 零污染
- **为什么报告先行、grilling 后置**：最常见的失败就是弱模型跳过报告直接就第一个想法开问（文档页："borderline unusable"）——设计意图明确是 "report comes first"
- 与 codebase-design 的分工：本 skill **找** module，codebase-design 是**设计**它的工作台

**调用关系**：开场 `codebase-design`（取词汇）→ `grilling` + `domain-modeling`（Phase 3）→ 按需再调 `codebase-design`（design-it-twice）。

## setup-matt-pocock-skills — 每仓库跑一次的前置配置

**定位**：回答三个问题（issue 在哪、triage label 叫什么、domain 文档放哪），把答案写成 `docs/agents/` 下的 markdown——**其他所有 engineering skill 的 precondition**。

**解决什么**：triage / to-spec / to-tickets / implement / wayfinder 都要读写 issue tracker——不知道该调 `gh`、写 `.scratch/` 还是别的，它们就只能瞎猜（"start guessing where your issues go, or apply labels your tracker doesn't have"）。

**五步**：Explore（读现状：`git remote -v`、AGENTS.md、GLOSSARY、monorepo 信号、triage 是否安装）→ 一节一答地问（**每节先给推荐答案**让用户一词确认）→ 确认草稿 → 写文件（`CLAUDE.md` 存在则编辑之，否则 `AGENTS.md`，都无则**问用户**，绝不代选）→ Done。

三个 tracker 选项：**GitHub** / **GitLab** / **Local markdown**（`.scratch/<feature>/`，solo 或无 remote 的完整选项，不是降级）/ **Other**（Jira、Linear……用户用一段话描述 workflow，**原样记录为自由文本**）。

**为什么这样设计**：
- **配置即 markdown、配置在 repo 里**："Those files are the only thing that varies between repos. The skills themselves are identical everywhere"——这就是整个 set 不绑 GitHub 的原因；改 skill 文件换 tracker 也会被 `npx skills update` 覆盖
- 三个 tracker 模板都带**翻译表**（"publish to the issue tracker" 在你的 tracker 里是什么意思）和 **Wayfinding operations** 节（wayfinder 的 map/ticket/blocking/frontier 操作）
- **不做 per-user 配置中心**：想在这配 grilling 节奏？拒绝——"skills stay opinionated and take no per-user config. Preferences belong in your CLAUDE.md"

**调用关系**：不调用任何 skill；但**探测** triage 是否安装（决定写不写 `triage-labels.md`）。

## to-spec — 把对话合成 spec

**定位**：把**当前会话**（已完成的讨论）合成为一份 spec 发布到 issue tracker——**no interview, just synthesis**，记录你已做的决定，不做新决定。

**解决什么**："Context windows end"——grilling 中敲定的一切（解法形状、吵过的选择、刻意拒绝的东西）都在一个即将被 clear 的对话里。spec 是决策存档，让 fresh session 无需你重新解释就能接手。触发条件：**只有跨多 session 的构建才值得这一步**；单 session 直接 `/implement`。

**三步**：① Explore repo → ② **Sketch the seams（唯一的人工门控）**——勾勒测试该 feature 的 seam：优先既有 seam、用**尽可能高的 seam**、越少越好、**理想数量是一**，必须与用户确认 → ③ 按 模板写 spec 发布，打 `ready-for-agent`（含义是"无需再 triage"，不是"照此实施"）。

**spec 模板**：Problem Statement → Solution → User Stories（LONG、编号）→ **Implementation Decisions**（module 与 interface、schema、API 契约；**禁文件路径与代码片段**——很快过期；例外：prototype 产出的 state machine/reducer/schema 可以内联并注明来源）→ Testing Decisions → Out of Scope。

**为什么这样设计**：
- **Seams before prose**：下游 `tdd` **只在预先约定的 seam 写测试**、`code-review` 会把没人约定过的 seam 当 finding——"Both connections go through this document"，所以 seam 对话必须在这里完成，不能留给实现阶段
- **为什么不采访**：到这一步决定已做完；它与 grill-with-docs 共享同一个 context window 才成立（**`/to-spec` 与 `/to-tickets` 之间不要 clear/compact**）
- 与 wayfinder 的衔接：map 清空后喂 `/to-spec #<map_issue>`——它负责把散落的决策 collapse 成可构建计划

**调用关系**：不调用 skill；通过共享文档被 `tdd`（seam 约定）和 `code-review`（Spec 轴）消费。

## to-tickets — 曳光弹工单

**定位**：把 plan、spec 或对话拆成一组 **tracer-bullet ticket**，每张票声明 **blocking edges**（阻塞边），发布到 tracker——本地是文本边，真实 tracker 是原生 blocking link。

**解决什么**：**最常见的错误拆法是按层横切**。文档页引用一个真实复盘：26 张按层切的票，每关一张要跑约 20 次 agent，四分之三是返工，"post-mortem traced every failure class back to the horizontal slicing"。

**工作流程**：① Gather context → ② Explore（找 **prefactor** 机会："Make the change easy, then make the easy change"）→ ③ **Draft vertical slices**——每片窄但**完整穿过每一层**（schema、API、UI、tests）、完成的片**独立可 demo**、每片**装得进一个全新 context window**、prefactor 排最前 → ④ **Quiz the user（人工门控）**：编号列表呈现每票的 Title / Blocked by / What it delivers，问粒度对吗、阻塞边真实吗、要不要合并/再拆，**迭代到批准为止** → ⑤ Publish（本地一票一文件按依赖序编号；真实 tracker 优先原生 blocking 关系；默认打 `ready-for-agent`）。

**Wide refactor 例外**：按 **expand–contract** 排序——expand（新形态并存，零破坏）→ 按爆炸半径分批 migrate（CI 保持 green）→ contract（删旧形态）。

**为什么这样设计**：
- **判别法**："问每张票：完成后我能 demo 什么？答不出就是 horizontal slice"——vertical slice "owns everything it grades"（验收标准只考自己交付的东西）
- **"The edges are the point of the artifact"**：tracker 只决定边能否被机器执行；发布后按 **frontier**（所有 blocker 已完成的票）推进
- **为什么 quiz**：模型默认原子单元、丢掉有意义的分组（过度拆分是最多人上报的问题）——发布前的人审是唯一矫正点，"Nothing reaches the tracker until you approve"
- **为什么一票一文件**：v1.1 的单文件 tickets.md 造成并行 agent 写入的 race condition（文档页记录的 bug）

**调用关系**：不调用 skill；产物被 `implement`（逐票）或 `implement-spec`（整图并行）消费。

## implement — 逐票落地

**定位**：把已决定的工作落成代码：在预先约定的 seam 上驱动 `/tdd`，收尾跑 `/code-review`，然后 commit——**绝不重开计划**。SKILL.md 只有 17 行。

**解决什么**："'build this' 式 agent 边建边重新设计"——文档页："It never reopens the plan. There is no interview, no clarifying round, no proposal of a different approach... That is what separates it from typing 'build this' at a fresh agent." 它是链条里"信任上游"的一环："It does not re-validate the shape of what it was handed, so a badly-structured map or a horizontally-layered ticket gets built as written."

**工作流程**：定位输入（ticket 引用则抓取并**先陈述其标题**再开工——防 `#2` 被解析到别的编号列表）→ 读票、定 seam → 调 `tdd`（"where possible, at pre-agreed seams"）→ **经常跑 typecheck 和单测试文件**，全套测试只在结束时跑一次 → 调 `code-review` → **commit 到当前分支**（不建分支、不问、不关票）。

**为什么这样设计**：
- **为什么极简（17 行）**：纪律全部外置到它调用的两个 skill（tdd 管测试质量、code-review 管收尾），implement 只编排顺序——与 grill-with-docs 的一行委托同一哲学
- **为什么全套测试只跑一次**：反馈经济学——高频小回路 + 低频全量回路
- **为什么一次一票、票间 `/clear`**：每张票自包含；多 session 共享一个 checkout 是灾难（文档页实录：一个下午三次事故——`git commit --amend` 落到别人的 commit、stash 消失、commit 上错分支）；并行需求交给 implement-spec 的 worktree 方案

**调用关系**：`tdd`（构建期间）+ `code-review`（收尾）。

## implement-spec — 整图并行落地

**定位**：把 `/to-spec` + `/to-tickets` 的产物在**一次 run 内全部落地**：编排者 agent 把 ticket 当 **task graph**，在 ready **frontier** 上并行派发 implementer subagent（各自在独立 worktree/分支上用 `/tdd` 构建），逐个合并进一条 **integration branch**，最后跑一次 `/code-review`。

**解决什么**：不想逐票手动开 session（"a spec may contain over 5 tickets"）；并行 checkout 冲突（用 worktree 隔离）；编排者窗口要装下整张图（所以通信必须稀疏）。

**工作流程**（9 步）：读 spec 与 tickets 理解 task graph（"The tickets are not a list of steps"）→ 可选 exploration subagent（探索笔记存 repo 外，让 implementer 专注实现）→ 建 integration branch（tracker 以 PR 收尾则在第一次 merge 后开 draft PR）→ **implementer subagent** 实现每张票（独立 worktree；调 `tdd`；**报告完成前先把 integration branch tip merge 进自己的分支**，保证主 merge 是 fast-forward）→ merger subagent 合并 → frontier 变化即再派（"maximum concurrency"）→ 全部完成后对 integration branch 跑一次 `code-review`，**所有 finding 交给单个 implementer 集中修复** → 收尾 → 清理 worktree。

**通信原则**："Communication to and from subagents should be sparse"——主要通过 **context pointer**（指向 spec、tickets、research notes），不复述指针可达的信息。

**为什么这样设计**：
- **为什么 code-review 只跑一次且在最后**：它对照**整个 spec** 审查——中途跑会把没建的票全读成失败，触发"build-review-build"数小时死循环（文档页真实案例：五票 feature 的 review-fix 循环跑了四小时）
- **为什么 implementer 先 merge integration tip**：把冲突解决前置到 implementer 侧——验收标准："Merges into the integration branch are fast-forwards, not conflict resolutions"
- **已知缺口**（文档页）：worktree 只装 git 跟踪的内容，gitignored fixtures 会静默跳过；两个 frontier 票仍可能撞同一文件（worktree 推迟而非消除冲突）——解法是补一条阻塞边

**调用关系**：`tdd`（每个 implementer 内部）+ `code-review`（最后对 integration branch 一次）。

## wayfinder — 迷雾中的决策地图

**定位**：为一个**大到超出单个 agent session**、且**通往 destination 的路还看不见**的工程，在 issue tracker 上绘制一张由 **decision tickets** 组成的 **shared map**，逐个解决决策、推进 frontier，直到雾散——**plan, don't do**（产出决策而非交付物）。

**解决什么**：grill-with-docs 的想法一个 session 装不下（greenfield、巨型 feature）——分界线就是 session 数："grill-with-docs for single-session planning, wayfinder for multi-session planning"。对抗瀑布陷阱：一次性规划 27 张票，到第 13 张其余全失效——wayfinder 用 fog of war + 渐进出票对抗。

**核心结构**：
- **The Map**：label 为 `wayfinder:map` 的 issue。**Map 是 index 不是 store**——"a decision lives in exactly one place, its ticket"，map 只给一行 gist + 链接。Body 五节：Destination（抵达是什么样子，命名它是绘图第一动作）/ Notes / Decisions so far / **Not yet specified（雾）** / Out of scope
- **四种票型**（每张要么 HITL 要么 AFK）：
  | 票型 | 模式 | 由什么解决 |
  |---|---|---|
  | `research` | AFK | 调 `research` 的 subagent |
  | `prototype` | HITL | 调 `prototype` 做可反应的粗糙实物 |
  | `grilling` | HITL | 双调 `grilling` + `domain-modeling`（默认票型） |
  | `task` | 皆可 | 手工活阻塞了决策（注册服务、开权限）——唯一"做而不决"的票型 |
- **Fog of war**：刻意不画看不见的图。判据："Ticket when the question is already sharp; Not yet specified when you can't yet phrase it that sharply"
- **Claim 机制**：开工前先把票 assign 给驱动的 dev——"That assignee *is* the claim"；**Frontier = open + unblocked + unclaimed**；**Refer by name**（人类可读叙述用票的名字，绝不裸 `#42`——"A wall of `#42, #43, #44` is illegible"）

**两种调用模式**（共同铁律："never resolve more than one ticket per session"，唯一例外是 research 票）：
- **Chart the map**：Name the destination（grilling + domain-modeling）→ 广度优先铺开（门控：**如果完全没有雾——"you don't need a map. Stop and ask the user"**）→ 建 map → 建现在能 specify 的子票、第二遍连线 blocking 边 → **并行点火 research subagent**（每张 research 票一个，发现写到 `research/<name>` 一次性分支，永不 merge）→ 停——"charting is one session's work; it hand-resolves nothing"
- **Work through the map**：低分辨率加载 → 选票（frontier 顺序第一张）、**先 claim** → 按 label 类型解决（"Read the label, not just the body"）→ 记录解决（resolution comment → close → map 的 Decisions so far 加 context pointer）→ 补新票、让雾毕业；发现某票越过 destination → **rule it out of scope** 而非在路线上解决

**汇入主流程**：地图清空后 **"it hands off, it doesn't build"**——在 `/to-spec` 汇入，把链接的决策 collapse 成可构建计划；直接 `/implement` 只适用于"结果确实很小"。

**为什么这样设计**：
- **为什么 plan, don't do**："The pull to just do the work is usually the signal you've reached the edge of the map"——规划与执行隔离在两个 context 里。文档页记录了它最出名的失败：agent 在会话中往**自己写的** Notes 里写 "this map carries execution"，后续 session 读回当成许可直接写产品代码
- **为什么一张票 = 一个 100K session**：票是 context 的计量单位
- **为什么 HITL 铁律**："the agent never stands in for the human's side of it"——agent 自问自答 grilling 问题即违规

**调用关系**：`grilling` + `domain-modeling`（多场景）、`research`（research 票）、`prototype`（prototype 票）——四个积木全用上了。

## retro — 复盘环境，不复盘代码

**定位**：对一次编码 session 做回顾，**按严重度从高到低**提出对 agent **environment** 的改进候选——**改环境、不改代码；只提议、不动手**。

**解决什么**："同一个错误反复发生"——"Mechanical mistakes become deterministic checks; judgement calls become coding standards"。核心推论：**"AGENTS.md 里一句新规则"几乎总是错误的修复位置**（它无条件加载进每个 session，稀释一切）。

**四步**：① 调 `writing-for-agents` 取写作风格 → ② 读 primary sources（默认当前 session——挣扎还在 context window 里，最佳情形）→ ③ 按七个类别找候选：
- **Navigation**：找信息耗时 → 加 navigation pointer
- **Automated checks**：先读 repo 自己的 check 命令——"a check that already exists but sits unwired is the finding, not a reinvention"；**没有 guardrail 本身就是 finding**："an un-linted repo is a standing missed opportunity, not a neutral default"
- **Coding standards**：**先给违规分类**——mechanical（固定语法模式）一律做成确定性检查，"Default to building the check over writing the rule"（"a check can fail and a sentence in a standards file can't"）；CODING_STANDARDS.md 只留给 judgement calls
- **Global AGENTS.md / Tool economy / No-ops / Information access**（把关键信息接到 agent 够得着的地方）
④ 按严重度排序呈现，等用户挑选。

**Reference 节的关键框架**：**Implementation vs Review**——实现 agent 的 context pressure 最大（探索+写码+调试），review agent 最小（只拿 diff）→ **"the review agent should be responsible for imposing coding standards, not the implementation agent"**——规则要放在有空间执行它的地方。

**为什么这样设计**：
- **为什么候选必须锚定 session 时刻**：对抗最强批评——"the AI tends to forget the struggles from the middle of the session and invent generic advice"；"Discard any candidate you can't trace to a specific moment"
- **为什么不是 memory system**："It does not store what happened. It changes the environment so the mistake cannot happen again"
- 与 improve-codebase-architecture 分工：那个输入是**代码**、改代码结构；retro 输入是 **session 记录**、改 agent 周围的环境——"You use both; neither replaces the other"

**调用关系**：`writing-for-agents`（唯一调用者）。
